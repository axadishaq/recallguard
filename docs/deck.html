RecallGuard is a multi-agent recall checker for independent pharmacies. It takes the pharmacy's shelf stock, cross-checks it against real FDA recall reports, and produces a cited action list: what to pull now, what to quarantine, what is cleared. It also remembers what staff already handled.

THE PROBLEM

Matching FDA recalls to the shelf is manual, slow, and easy to get wrong

1,436

drug recall reports since Jan 2025 in openFDA, each listing NDCs and lots in free text

3 formats

FDA codes are 10-digit (4-4-2, 5-3-2, 5-4-1); pharmacy systems store 11 digits with no dashes

0 memory

nothing tracks which recalls staff already pulled, so every check starts from scratch

Three things make recall checks hard for a small pharmacy. Volume: over 1,400 drug recall reports since January 2025 in openFDA alone. Formats: the FDA publishes 10-digit NDCs in three shapes, but pharmacy and wholesaler systems store an 11-digit code, so a simple lookup misses. And no memory: nobody tracks what was already handled. The lot details are free text, like "subset of lot 2199821, specific serial numbers" or "all lots within expiry".

WHO IT’S FOR

The pharmacist at an independent community pharmacy

No recall team

Chains have compliance staff and integrated systems. A small pharmacy has one pharmacist, a shelf export and the FDA website.

High stakes either way

Missing a Class I lot puts patients at risk. Over-pulling on a name match wastes stock and time.

Needs proof, not a guess

Every action must point to the FDA record and the exact lot text that justifies it.

Weekly, not once

Recalls keep arriving. Each check should surface only what is new or still open.

Our user is the pharmacist at an independent community pharmacy. They don't have a recall team or an integrated compliance system. They need two things: proof for every action, because both missing a recall and over-pulling stock have real costs, and continuity, because this is a weekly job, not a one-off.

Evaluator

Reporter

Cited action list, new vs resolved

revise plan

Zetaris

inventory · NDC directory · recalls · recall↔NDC

Risk agent

Class I and sterility escalations

Every step lands in a live trace, including which Nightshift model handled it.

This is the architecture. The Planner scopes the request. The Matcher runs SQL through Zetaris, joining shelf stock to the NDC directory and to the recall reports. The Evaluator critiques each match: is the evidence strong, and is our lot actually covered? When evidence is missing, it sends the work back to the Planner, which revises the plan: that's the orange loop. Severe cases escalate to the Risk agent. The Reporter writes the action list, and H-MEM gives both the Planner and the Reporter memory across sessions.

EXPLAINING WHY

The Evaluator reads the FDA’s free-text lot field and quotes it

“All lots within expiry.”

All lots → pull now

Our lot X240137 isn’t named, but the recall covers every lot.

“Subset of Lot 2199821 … Specific Serial Numbers being Recalled”

Partial → quarantine

Hold the units and check each serial number before releasing any.

“Lot #: 1239521, 1237454, Exp. Date 10/2027”

Not listed → cleared

Same product, but our lot X240211 isn’t recalled. No stock wasted.

On Class I or ambiguous text, a Nemotron model cross-checks the rules. If they disagree, the item is downgraded to manual verification, never silently decided.

This is the "explain why" part. Every decision quotes the FDA's own lot text. Three real recalls, three different outcomes. For high-stakes Class I recalls or ambiguous text, the Evaluator asks a Nemotron model through Nightshift to read the text too. If the model and the rules disagree, RecallGuard doesn't pick one; it asks the pharmacist to verify.

This is the Meterless Engine in a working feature. H-MEM stores every finding with its FDA source. When the pharmacist marks something resolved, that note goes into long-term memory as a user correction, linked to the finding. In the next session the alert is suppressed and the note is shown, while still-open items are marked as previously flagged. Our test suite checks exactly this, and Meterless's own H-MEM conformance suite passes 13 of 13.

WHAT’S DIFFERENT

It refuses to guess. Weak evidence goes back for more, and disagreement goes to a human.

Evidence ladder: exact package NDC → inferred product code → name + firm; name-only matches are rejected

Rules + model: deterministic lot parsing, with Nemotron as a second reader on high-stakes text

Memory as governance: staff corrections in H-MEM change what future runs report

What's unique: RecallGuard is built to refuse to guess. Evidence is ranked, and weak evidence triggers a re-plan instead of an answer. Rules and a model each read the lot text, and when they disagree a human decides. And memory isn't just recall: a pharmacist's correction in H-MEM changes what every future run reports.

TECH STACK AND RELIABILITY

Small, typed, and built to keep running when a service is down

Stack

  • Node.js + TypeScript, zero framework
  • Zetaris SQL REST API · local SQL engine for sample mode
  • Meterless H-MEM engine · Nightshift client
  • Web UI with live trace (server-sent events) + CLI

Reliability

  • Zetaris down → cached openFDA sample, flagged in the trace
  • No model → deterministic agents, same SQL
  • Bounded loop (3 iterations), timeouts everywhere
  • 6 app tests + 13/13 H-MEM conformance checks
The stack is deliberately small: Node and TypeScript, with no agent framework. The important part is reliability. Each layer degrades on its own: if Zetaris is down we use the cached openFDA sample, and if no model is reachable the agents fall back to deterministic logic running the same SQL. The trace always says which path ran. Loops are bounded and every call has a timeout.
